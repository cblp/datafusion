# Детерминированный `sum` для чисел с плавающей точкой

## Задача

Сделать так, чтобы результат `sum` для чисел с плавающей точкой не зависел от
порядка суммирования: от разбиения данных на партиции и батчи, от перемешивания
строк, от плана выполнения.

Раньше `sum` складывал числа с плавающей точкой в порядке, который определяется
планом выполнения. Сложение `f64` не ассоциативно, поэтому на одних и тех же
данных `sum` мог давать результаты, отличающиеся в последних битах, в том числе
при повторе того же запроса.

## Результат

Встроенный `sum` для чисел с плавающей точкой вычисляет точную сумму входных
значений и один раз округляет её до ближайшего `f64` (к чётному при равенстве).
Корректно округлённый результат единственный, поэтому он не зависит от порядка.
Для остальных типов (целые, `DECIMAL`, интервалы) `sum` не изменился.

- Реализация — `datafusion/functions-aggregate/src/sum/float.rs`; встроенный
  `Sum` (`sum.rs`) выбирает её для `Float64`, к которому `sum` приводит все типы
  с плавающей точкой.
- Точная сумма хранится в [`bitrep::SumF64`](https://docs.rs/bitrep):
  2176-битное целое с фиксированной точкой в единицах 2⁻¹⁰⁷⁴ (наименьшее
  субнормальное `f64`). Любое конечное `f64` представляется в нём точно, а
  целочисленное сложение ассоциативно и коммутативно. Запаса хватает на 2⁶³
  значений без переполнения.
- `NaN` и `±inf` учитываются отдельно: любой `NaN` или одновременно `+inf` и
  `−inf` дают `NaN`, бесконечность одного знака даёт её же. Если точная сумма
  выходит за диапазон `f64`, результат `±inf`, как при обычном сложении.
- Пустой вход или только `NULL` дают `NULL`.
- Состояние частичной агрегации — `SumF64::to_bytes()` в колонке
  `FixedSizeBinary`; слияние партиций — сложение этих чисел.
- Детерминированы все пути вычисления `sum`: без `GROUP BY` (`Accumulator`), с
  `GROUP BY` (`GroupsAccumulator`, `Vec<SumF64>` по номеру группы), `DISTINCT`
  и скользящие оконные рамки (`ROWS BETWEEN ...`), из которых значения не только
  добавляются, но и удаляются.
- Для `Float64` отключены две оптимизации, которые подменяли точную сумму:
  перезапись `sum(x + c)` в `sum(x) + c * count(x)` и подстановка суммы из
  статистики.
- Тесты — `datafusion/sqllogictest/test_files/sum_float.slt` и юнит-тесты
  округления в `sum/float.rs`. В двух местах обновлены существующие тесты: в
  снимке `dataframe::register_table` старые суммы заменены точными (совпадают с
  `math.fsum` из Python), а тесты `partial_reduce_*` в `datafusion-physical-plan`,
  которые вручную собирали состояние `sum` для `Float64`, переведены на `Int64`.

## Демонстрация

Для сравнения используется `avg(x) * count(x)`: `avg` по-прежнему складывает
`f64` обычным сложением, в порядке, который определяется планом выполнения.

Один и тот же набор чисел суммируется в разном порядке:

```sql
-- 1 млн чисел разных знаков, величины от 1 до 1e20
CREATE TABLE t AS
    SELECT (random() - 0.5) * pow(10, random() * 20) AS x
    FROM generate_series(1, 1000000);

-- те же числа, перемешанные
CREATE TABLE t_shuffled AS SELECT x FROM t ORDER BY random();

-- 1. исходный порядок
SELECT sum(x), avg(x) * count(x) FROM t;

-- 2. перемешанный порядок
SELECT sum(x), avg(x) * count(x) FROM t_shuffled;

-- 3. исходный порядок, но батчи по 100 строк вместо 8192
SET datafusion.execution.batch_size = 100;
SELECT sum(x), avg(x) * count(x) FROM t;
```

Результат одного прогона (данные случайные, числа будут другими):

| запрос                 | `sum(x)`              | `avg(x) * count(x)`   |
| ---------------------- | --------------------- | --------------------- |
| 1. исходный порядок    | 3.3094547560938104e21 | 3.309454756093809e21  |
| 2. перемешанные строки | 3.3094547560938104e21 | 3.3094547560938036e21 |
| 3. батчи по 100        | 3.3094547560938104e21 | 3.309454756093809e21  |

На нескольких числах:

```sql
-- порядок слагаемых не меняет результат
SELECT sum(x) FROM (VALUES (1e16), (1.0), (-1e16)) AS v(x); -- 1.0
SELECT sum(x) FROM (VALUES (1.0), (1e16), (-1e16)) AS v(x); -- 1.0 (обычное сложение даёт 0.0)

-- точная сумма, округлённая один раз
SELECT sum(x) FROM (VALUES (0.1), (0.2), (0.3)) AS v(x); -- 0.6 (обычное сложение даёт 0.6000000000000001)
```

Перемешивание в подзапросе
(`SELECT sum(x) FROM (SELECT x FROM t ORDER BY random())`) для демонстрации не
подходит: оптимизатор выбрасывает сортировку под агрегатом.

### Разное число партиций

Таблица в памяти (`CREATE TABLE ... AS`) получает партиции по числу ядер
независимо от `datafusion.execution.target_partitions`, и при запросах эта
настройка на неё не влияет. Parquet-файл с мелкими row group'ами DataFusion при
каждом запросе делит между `target_partitions` партициями:

```sql
-- row group по 10 000 строк, чтобы файл можно было делить между партициями
COPY (
    SELECT (random() - 0.5) * pow(10, random() * 20) AS x
    FROM generate_series(1, 1000000)
) TO '/tmp/t.parquet'
    STORED AS PARQUET
    OPTIONS ('format.max_row_group_size' '10000');
CREATE EXTERNAL TABLE tp STORED AS PARQUET LOCATION '/tmp/t.parquet';

SET datafusion.execution.target_partitions = 1;
SELECT sum(x), avg(x) * count(x) FROM tp;

SET datafusion.execution.target_partitions = 2;
SELECT sum(x), avg(x) * count(x) FROM tp;

SET datafusion.execution.target_partitions = 4;
SELECT sum(x), avg(x) * count(x) FROM tp;

SET datafusion.execution.target_partitions = 12;
SELECT sum(x), avg(x) * count(x) FROM tp;
SELECT sum(x), avg(x) * count(x) FROM tp; -- тот же запрос ещё раз
```

Результат одного прогона:

| партиций   | `sum(x)`             | `avg(x) * count(x)`  |
| ---------- | -------------------- | -------------------- |
| 1          | 4.702909434384429e19 | 4.702909434384643e19 |
| 2          | 4.702909434384429e19 | 4.702909434384715e19 |
| 4          | 4.702909434384429e19 | 4.702909434384679e19 |
| 12         | 4.702909434384429e19 | 4.702909434384672e19 |
| 12, повтор | 4.702909434384429e19 | 4.70290943438464e19  |

При обычном сложении результат меняется даже при повторе того же запроса:
частичные суммы партиций приходят на финальную стадию в порядке, который
зависит от планирования потоков, и складываются в этом порядке.

## Производительность

Точное суммирование дороже обычного сложения, особенно при большом числе групп.
Для целых и других типов производительность `sum` не изменилась.

### Микробенчмарки

`cargo bench -p datafusion-functions-aggregate --bench sum`, 8192 значения;
случаи для `f64` и `update batch` добавлены в бенчмарк. «Было» — исходный код
ветки до изменения `sum`, «стало» — текущий; macOS.

| случай                               | было, мкс | стало, мкс    | изменение |
| ------------------------------------ | --------- | ------------- | --------- |
| `i64`, все случаи                    | 2.2–11.6  | без изменений |    шум    |
| `f64` `update_batch`, 1 группа       |     20.7  |      22.7     |    +8%    |
| `f64` `update_batch`, 1000 групп     |      2.2  |      27.4     |    ×12    |
| `f64` `convert_to_state`             |      2.7  |     107       |    ×40    |

`convert_to_state` используется, когда DataFusion пропускает частичную
агрегацию при большом числе групп: раньше значения передавались дальше как есть,
теперь для каждой строки собирается состояние в 281 байт.

### Запросы в `datafusion-cli`

Условия: release-сборка `datafusion-cli`, macOS, данные `random() * 1e6` из
`generate_series`; время из вывода `datafusion-cli` (`Elapsed`). Замеры сделаны,
когда детерминированная сумма была отдельной функцией `det_sum` с теми же
аккумуляторами, рядом со старым `sum`.

Без `GROUP BY`, 50 млн строк,
`SELECT f(random() * 1e6) FROM generate_series(1, 50000000)`, лучшее из двух:

| старый `sum` | 0.062 с |
| новый `sum`  | 0.066 с |

С `GROUP BY`, 20 млн строк, `SELECT count(s) FROM (SELECT f(random() * 1e6) s
FROM generate_series(1, 20000000) t(v) GROUP BY v % N)`, лучшее время из 3
запусков. Промежуточная версия без `GroupsAccumulator` использовала стандартный
адаптер `GroupsAccumulatorAdapter` с отдельным `Accumulator` на каждую группу.

| групп (N)  | старый `sum` | без `GroupsAccumulator` | новый `sum` | ускорение от `GroupsAccumulator` |
| ---------- | ------------ | ----------------------- | ----------- | -------------------------------- |
|          1 | 0.032 с      | 0.033 с                 | 0.033 с     | —                                |
|        100 | 0.030 с      | 0.037 с                 | 0.034 с     | —                                |
|     10 000 | 0.032 с      | 0.180 с                 | 0.054 с     | 3.3×                             |
|  1 000 000 | 0.062 с      | 2.46  с                 | 0.339 с     | 7.3×                             |
| 10 000 000 | 0.091 с      | 3.65  с                 | 0.492 с     | 7.4×                             |

Старый `sum` в этой таблице — из прогона с `GroupsAccumulator`; в прогоне без
него время старого `sum` было таким же в пределах шума (0.030–0.095 с).

При миллионах групп новый `sum` медленнее старого примерно в 5,5 раза. Это цена
состояния: около 290 байт на группу против 8 у обычной суммы, и столько же байт
на группу передаётся между фазами агрегации.
