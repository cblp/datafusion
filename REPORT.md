# Детерминированная сумма `det_sum` в `datafusion-cli`

## Задача

Добавить в `datafusion-cli` агрегатную функцию `det_sum :: Float64 -> Float64`,
результат которой не зависит от порядка суммирования: от разбиения данных на
партиции и батчи, от перемешивания строк, от плана выполнения.

Встроенный `sum` складывает числа с плавающей точкой в порядке, который
определяется планом выполнения. Сложение `f64` не ассоциативно, поэтому на одних
и тех же данных `sum` может давать результаты, отличающиеся в последних битах.

## Результат

`det_sum` вычисляет точную сумму входных значений и один раз округляет её до
ближайшего `f64` (к чётному при равенстве). Корректно округлённый результат
единственный, поэтому он не зависит от порядка.

- Функция регистрируется в `datafusion-cli/src/main.rs` и доступна в обычном
  `datafusion-cli`.
- Реализация — `datafusion-cli/src/det_sum.rs`.
- Точная сумма хранится в [`bitrep::SumF64`](https://docs.rs/bitrep):
  2176-битное целое с фиксированной точкой в единицах 2⁻¹⁰⁷⁴ (наименьшее
  субнормальное `f64`). Любое конечное `f64` представляется в нём точно, а
  целочисленное сложение ассоциативно и коммутативно. Запаса хватает на 2⁶³
  значений без переполнения.
- `NaN` и `±inf` учитываются отдельно: любой `NaN` или одновременно `+inf` и
  `−inf` дают `NaN`, бесконечность одного знака даёт её же. Если точная сумма
  выходит за диапазон `f64`, результат `±inf`, как при обычном сложении.
- Пустой вход или только `NULL` дают `NULL`, как у `sum`.
- Состояние частичной агрегации — `SumF64::to_bytes()` в колонке
  `FixedSizeBinary`; слияние партиций — сложение этих чисел.
- Реализованы оба интерфейса аккумулятора: `Accumulator` (агрегация без
  `GROUP BY`) и `GroupsAccumulator` (`Vec<SumF64>` по номеру группы, для
  `GROUP BY`).

## Демонстрация

Один и тот же набор чисел суммируется в разном порядке:

```sql
-- 1 млн чисел разных знаков, величины от 1 до 1e20
CREATE TABLE t AS
    SELECT (random() - 0.5) * pow(10, random() * 20) AS x
    FROM generate_series(1, 1000000);

-- те же числа, перемешанные
CREATE TABLE t_shuffled AS SELECT x FROM t ORDER BY random();

-- 1. исходный порядок
SELECT count(*), sum(x), det_sum(x) FROM t;

-- 2. перемешанный порядок
SELECT count(*), sum(x), det_sum(x) FROM t_shuffled;

-- 3. исходный порядок, но батчи по 100 строк вместо 8192
SET datafusion.execution.batch_size = 100;
SELECT count(*), sum(x), det_sum(x) FROM t;
```

Результат одного прогона (данные случайные, числа будут другими, но `sum`
меняется, а `det_sum` нет):

| запрос                 | `sum(x)`              | `det_sum(x)`          |
| ---------------------- | --------------------- | --------------------- |
| 1. исходный порядок    | 2.7266296776395787e21 | 2.7266296776395797e21 |
| 2. перемешанные строки | 2.7266296776395776e21 | 2.7266296776395797e21 |
| 3. батчи по 100        | 2.726629677639587e21  | 2.7266296776395797e21 |

На нескольких числах:

```sql
-- порядок слагаемых меняет результат sum, но не det_sum
SELECT sum(x), det_sum(x) FROM (VALUES (1e16), (1.0), (-1e16)) AS v(x); -- 1.0 | 1.0
SELECT sum(x), det_sum(x) FROM (VALUES (1.0), (1e16), (-1e16)) AS v(x); -- 0.0 | 1.0

-- точная сумма, округлённая один раз
SELECT sum(x), det_sum(x) FROM (VALUES (0.1), (0.2), (0.3)) AS v(x); -- 0.6000000000000001 | 0.6
```

Перемешивание в подзапросе
(`SELECT sum(x) FROM (SELECT x FROM t ORDER BY random())`) для демонстрации не
подходит: оптимизатор выбрасывает сортировку под агрегатом.

### Разное число партиций

Таблица в памяти (`CREATE TABLE ... AS`) получает партиции по числу ядер
независимо от `datafusion.execution.target_partitions`, и при запросах эта
настройка на неё не влияет. Parquet-файл с мелкими row group'ами DataFusion при
каждом запросе делит между `target_partitions` партициями:

```sql
-- row group по 10 000 строк, чтобы файл можно было делить между партициями
COPY (
    SELECT (random() - 0.5) * pow(10, random() * 20) AS x
    FROM generate_series(1, 1000000)
) TO '/tmp/t.parquet'
    STORED AS PARQUET
    OPTIONS ('format.max_row_group_size' '10000');
CREATE EXTERNAL TABLE tp STORED AS PARQUET LOCATION '/tmp/t.parquet';

SET datafusion.execution.target_partitions = 1;
SELECT sum(x), det_sum(x) FROM tp;

SET datafusion.execution.target_partitions = 2;
SELECT sum(x), det_sum(x) FROM tp;

SET datafusion.execution.target_partitions = 4;
SELECT sum(x), det_sum(x) FROM tp;

SET datafusion.execution.target_partitions = 12;
SELECT sum(x), det_sum(x) FROM tp;
SELECT sum(x), det_sum(x) FROM tp; -- тот же запрос ещё раз
```

Результат одного прогона (число групп файлов 1, 2 и 12 подтверждено
`EXPLAIN`):

| партиций   | `sum(x)`              | `det_sum(x)`          |
| ---------- | --------------------- | --------------------- |
| 1          | 4.0847401267492526e21 | 4.0847401267492553e21 |
| 2          | 4.0847401267492516e21 | 4.0847401267492553e21 |
| 4          | 4.084740126749252e21  | 4.0847401267492553e21 |
| 12         | 4.084740126749253e21  | 4.0847401267492553e21 |
| 12, повтор | 4.0847401267492526e21 | 4.0847401267492553e21 |

При 12 партициях `sum` меняется даже при повторе того же запроса: частичные
суммы партиций приходят на финальную стадию в порядке, который зависит от
планирования потоков, и складываются в этом порядке. То же видно на таблице в
памяти: повторяя `SELECT sum(x), det_sum(x) FROM t`, можно получить разные
значения `sum`.

## Производительность

Условия: release-сборка `datafusion-cli`, macOS, данные
`random() * 1e6` из `generate_series`; время из вывода `datafusion-cli`
(`Elapsed`).

### Без `GROUP BY`

50 млн строк, `SELECT f(random() * 1e6) FROM generate_series(1, 50000000)`;
собственная реализация — один запуск, `bitrep` — лучшее из двух:

| реализация `det_sum`                      | `sum`   | `det_sum` |
| ----------------------------------------- | ------- | --------- |
| `bitrep::SumF64`                          | 0.062 с | 0.066 с   |

### С `GROUP BY`: без `GroupsAccumulator` и с ним

20 млн строк, `SELECT count(s) FROM (SELECT f(random() * 1e6) s FROM
generate_series(1, 20000000) t(v) GROUP BY v % N)`, лучшее время из 3
запусков. Без `GroupsAccumulator` DataFusion использует стандартный адаптер
`GroupsAccumulatorAdapter` с отдельным `Accumulator` на каждую группу.

| групп (N)  | `sum`   | `det_sum` без `GroupsAccumulator` | `det_sum` с `GroupsAccumulator` | ускорение |
| ---------- | ------- | --------------------------------- | ------------------------------- | --------- |
|          1 | 0.032 с | 0.033 с                           | 0.033 с                         | —         |
|        100 | 0.030 с | 0.037 с                           | 0.034 с                         | —         |
|     10 000 | 0.032 с | 0.180 с                           | 0.054 с                         | 3.3×      |
|  1 000 000 | 0.062 с | 2.46  с                           | 0.339 с                         | 7.3×      |
| 10 000 000 | 0.091 с | 3.65  с                           | 0.492 с                         | 7.4×      |

`sum` в этой таблице — из прогона с `GroupsAccumulator`; в прогоне без него
время `sum` было таким же в пределах шума (0.030–0.095 с).

При миллионах групп `det_sum` медленнее `sum` примерно в 5,5 раза. Это цена
состояния: около 290 байт на группу против 8 у `sum`, и столько же байт на
группу передаётся между фазами агрегации.
